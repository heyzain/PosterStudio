# Poster Studio V2 implementation plan

The implementation scope was later updated to start with a fresh V2 workspace. The legacy audit and migration proposal below record the original plan. V2 uses a separate local workspace and does not import legacy folders.

## Phase 1 audit

The baseline is commit `64159dd` on `main`. The working tree was clean at inspection. This phase documents the upgrade for approval. Phase 2 begins after approval.

## Domain and storage

- **Collection.** Persist an immutable UUID and editable name, description, icon or cover reference, destination configuration, and schema revision in the collection manifest. The workspace registry stores collection UUID, last known path, and archive state. Resolve real paths for existing roots and reject duplicate or nested attachments. Archive is reversible and leaves the collection files in place. Renaming updates the name in metadata.
- **Content item.** Give each item a stable ID and retain its existing collection-local number as a separate field and folder name. Use the collection UUID and number for a deterministic legacy item ID, then persist the ID on write. Keep shared title, main artwork, master text, notes, artwork fallback text and theme, optional asset references, and timestamps. Use unknown timestamps for legacy records where trustworthy dates are unavailable. Preserve the original display order and never reuse numbers, including numbers held by trash or manually created directories.
- **Destination.** Store a stable collection-local ID, preset type, label, enabled state, optional URL and icon, and field definitions. Provide presets for Facebook, Instagram, Pinterest, LinkedIn, YouTube, X, Threads, and Custom website. Save custom website profiles locally so they can be reused in other collections. Each collection gets its own destination instance and editable schema when it attaches a profile.
- **Destination record.** Track selected destinations explicitly per item. Keep field values, planned date and optional time, status, actual publication date when known, and optional published URL per record. Disabling a destination prevents new assignment. Existing records remain accessible, including their calendar dates and history. Detaching a destination from an item retains its values so it can be reattached. A new item starts with no selected destinations.
- **Field definition.** Use stable IDs, labels, type, description, required state, defaults, display order, and supported validation rules. Support short text, long text, URL, tags, number, date/time, single select, checkbox, and stored image/file references. Use option IDs for single select so label changes preserve stored selections. Archive fields and options with saved values and provide restore actions. For an incompatible type change, create a replacement field and retain the original value under its original definition. Apply defaults when creating a destination record and validate required publishing fields when marking it Ready or Scheduled. Older records and partial drafts remain readable and editable.
- **Status.** Keep overall creative stage and destination status distinct. Derive Scheduled from pending planned dates. Derive Published from completion of the selected destinations and retain legacy manually assigned creative stages on migration. A completion action changes only the targeted destination, and imported dates remain date-only local calendar dates. Treat unknown historical publication dates as unknown.

Presets contain suggested fields rather than dedicated editor components. Facebook starts with caption and shared-image reference. Pinterest starts with title, description, tags, board, and image. LinkedIn starts with post text, image, optional link, and hashtags. Publishing controls are common to every destination. An image value can reference the shared artwork or a stored local asset, avoiding duplicate copies of the main image.

## Migration and write safety

1. Use the existing saved folder as the default legacy collection, with the display name **Mira, Zavi & Pip**. Allow additional external collection folders to be attached individually. On startup, keep broken or unavailable paths visible and report unreadable metadata before offering retry or reconnect.
2. Inspect the legacy root before writing. Detect invalid JSON, unsupported versions, orphaned folders, case-insensitive path collisions, and number conflicts. Show actionable errors that identify the affected path. A read failure must never be interpreted as an empty collection.
3. Create and verify a dated local backup of the original preferences and collection data, including original manifests, poster metadata, artwork, and trash. Keep the backup outside the active collection tree. Back up each legacy root before its first upgrade, and leave it available for recovery.
4. After verifying the backup, atomically publish the versioned collection manifest and then register it in preferences. Preserve `Posters/` and `.PosterStudioTrash/`. If registration fails after writing the manifest, reopen the folder using the same saved UUID and retry registration. Once a root has a V2 manifest, the older app's existing version check prevents it from writing there. Restore the verified backup to a separate location for rollback.
5. Read V1 item records through a compatibility adapter, including within a V2 collection. Map Facebook caption/date/posted and Pinterest title/description/tags/date/posted to fixed initial destination and field IDs. Preserve the existing Instagram-to-Facebook compatibility rules and store original Instagram information as historical data. Keep legacy values in the item file or its versioned history on first edit. Validate conversion against copies of both legacy formats before testing with any personal collection.
6. Serialize mutations per collection, validate before touching disk, and use atomic JSON replacement. For assets, write to a new managed file before updating the metadata pointer. Keep the previous reference usable until the metadata commit succeeds. Trash moves use an explicit operation and recovery must preserve number and identity. Test retries across asset, metadata, and registry failures.
7. Bind media addresses to the collection and item that registered the asset. Keep the renderer sandbox and narrow IPC calls. Validate IDs, sender, media path, and request shape in the main process. Reject filesystem escapes, including symlinks or junctions pointing outside managed storage. File fields use managed references from the file picker.

## Website icons

Accept public HTTP or HTTPS website URLs with no credentials. Keep icon retrieval in the main process and make it optional. Resolve and screen address candidates, pin connections to checked public addresses, and repeat checks for redirects. Apply request time, redirect, download size, and image dimension limits. Reject local and private-network destinations, including IPv6 and mapped addresses, and disallow unsupported schemes and ports. Fetch an icon from site metadata or the site's conventional favicon path, validate and decode supported raster formats, and cache a local copy. Use a local upload or the built-in globe when retrieval or decoding fails. Website profiles and saved icons remain usable offline.

## UI changes

| Screen | Planned change |
| --- | --- |
| Collections home | Keep the compact header, theme control, and Collections and Calendar navigation. Show each collection's name, cover or icon, content count, and destination icons. Provide Create Collection and Open Existing Folder actions. |
| Collection detail | Show name and description, configured destinations, Add Content, Settings, search, status filters, sorting, and the existing artwork grid. Label disconnected collections and offer reconnect from the same entry. |
| Content view and edit | Reuse the existing artwork preview and detail/editor layout. Edit shared content first, then choose destinations with tabs or compact sections for their generated fields. Keep copy per field and per tag. Provide manual status and dates, local folder access, and export of selected content. Preserve in-progress edits while switching between destination panels. |
| Collection settings | Group collection identity and cover, destination enablement and profiles, schema management, the root folder, and backup/export actions. Confirm archive and provide a restore list. Field removal goes through archive with the stored values available on restore. |
| Calendar | Keep month, today, selected-day agenda, quick planning, and completion controls. Show events across available collections with collection and destination filters. Route each event back to its owning collection and item, including when another collection contains the same poster number. |
| Browser preview | Keep the current browser demo and its saved changes available. Validate desktop collection behavior separately from the demo. |

Use the existing branding, charcoal surfaces, sage accent, and light theme. Keep collection and destination management in settings and reserve the main views for browsing, editing, and planning content.

## Risks and acceptance tests

| Risk | Acceptance check |
| --- | --- |
| Losing existing data during upgrade | Upgrade a temporary copy containing Facebook/Pinterest and older Instagram records, distinct original artwork, Unicode captions, multiline tags, completed and planned dates, gaps, custom ordering, and trash. Compare metadata and image bytes. Verify the backup and recover to a separate location. |
| Interrupted or repeated upgrades | Inject failures at backup, manifest commit, and registry update. Retry without duplicates or changes to original numbering. Confirm corrupt data and disconnected roots surface errors and remain available for recovery. |
| Two collections reuse the same poster number | Create two roots with item #001. Verify thumbnails, saves, calendar actions, exports, and trash moves target the intended collection. Rename and archive a collection, restore it, and verify the ID and content persist across a restart. |
| Settings and schema edits discard values | Add Facebook, Pinterest, LinkedIn, and a custom website. Test all remaining preset schemas. Rename, reorder, archive, and restore fields and options. Verify old values survive a restart and incompatible type changes. Reject malformed URLs, dates, numbers, option IDs, and file references. |
| One platform updates another | Mark LinkedIn Published while Facebook and Pinterest are Scheduled. Verify dates, status, and completion are independent in editor and calendar. Check legacy partial completion, undo, date-only rendering, quick planning, and cross-collection event routing. |
| Editor and gallery regressions | Check create/edit, artwork preview, replace/remove and trash; search by text or number; Draft/Ready/Scheduled/Published filters; sort; per-field and per-tag copy; theme switching; and browser demo persistence. Confirm new items start without destinations and the editor shows only destination fields selected for that item. |
| Unsafe or failed icon retrieval | Use controlled fixtures for HTTPS success, redirects to internal addresses, address changes, invalid image bytes, oversized responses, timeout, and offline behavior. Confirm custom uploads and the globe still work. Test path and IPC guards against invalid IDs and references. |
| Desktop behavior differs from unit tests | Run the Electron app with test preferences and disposable folders. Restart it and repeat the read, edit, quick-plan, manual completion, file open, and export flows offline. Verify the Windows package can start with the same workflows where tooling permits. |
